# ts-implscan

[![npm](https://img.shields.io/npm/v/@thomasrepnik/ts-implscan)](https://www.npmjs.com/package/@thomasrepnik/ts-implscan)
[![CI](https://github.com/thomasrepnik/ts-implscan/actions/workflows/ci.yml/badge.svg)](https://github.com/thomasrepnik/ts-implscan/actions/workflows/ci.yml)

**Spring-style `List<PaymentHandler>` injection for TypeScript.** Mark an interface with `ImplScan`, and a
build-time generator collects every class that implements it into a typed registry. For Angular,
it also generates the `InjectionToken`s and providers. Mark it with `Dispatchable` instead, and
you also get a generated dispatcher that forwards each call to the one applicable implementation.

## Installation

```sh
npm install --save-dev @thomasrepnik/ts-implscan
```

The package contains two things:

| What | How you use it |
|---|---|
| The `ImplScan` and `Dispatchable` marker interfaces | `import type { ImplScan } from '@thomasrepnik/ts-implscan'` |
| The `ts-implscan` CLI (the generator) | `npx ts-implscan`, or in a `package.json` script |

It's a dev dependency because it only runs at build time. The marker imports are type-only and
disappear when compiled, so nothing from this package ends up in your production bundle.
You need Node 22 or newer.

## Quick start

### 1. Mark an interface

Extend `ImplScan` to tell the generator to collect the interface's implementations:

```ts
// payment-handler.ts
import type { ImplScan } from '@thomasrepnik/ts-implscan';

export interface PaymentHandler extends ImplScan {
  name: string;
  pay(amount: number): string;
}
```

### 2. Implement it

Write implementations as usual, anywhere under `src/`. They must be exported:

```ts
// card-handler.ts
export class CardHandler implements PaymentHandler {
  name = 'card';
  pay(amount: number) {
    return `charged ${amount} to credit card`;
  }
}

// paypal-handler.ts
export class PaypalHandler implements PaymentHandler { ... }
```

### 3. Generate the registry and use it

Pick the variant for your project.

#### With Angular

Add the generator to your scripts, so it runs before every `ng serve` and `ng build`:

```json
"scripts": {
  "generate": "ts-implscan --target angular --project tsconfig.app.json --out src/app/generated/implscan-registry.ts",
  "prestart": "npm run generate",
  "prebuild": "npm run generate"
}
```

Register all implementations once:

```ts
// app.config.ts
import { provideImplscan } from './generated/implscan-registry';

export const appConfig: ApplicationConfig = {
  providers: [provideImplscan()],
};
```

Inject the list anywhere. This is the equivalent of Spring's `List<PaymentHandler>`:

```ts
import { PAYMENT_HANDLER_LIST } from './generated/implscan-registry';

@Injectable({ providedIn: 'root' })
export class PaymentService {
  private readonly handlers = inject(PAYMENT_HANDLER_LIST); // PaymentHandler[]

  payWithAll(amount: number) {
    return this.handlers.map((handler) => handler.pay(amount));
  }
}
```

Implementations can use DI themselves, for example `private readonly http = inject(HttpClient)`.
Mark them with `@Injectable()`, but **without** `providedIn: 'root'`. `provideImplscan()` already
creates one instance per implementation, so a root-provided implementation would exist twice.

<details>
<summary>What gets generated</summary>

```ts
// src/app/generated/implscan-registry.ts
// GENERATED by ts-implscan – do not edit
import { InjectionToken, type Provider } from '@angular/core';
import type { PaymentHandler } from '../payment/payment-handler';
import { CardHandler } from '../payment/card-handler';
import { PaypalHandler } from '../payment/paypal-handler';

export const PaymentHandlerImplementations: Array<new (...args: any[]) => PaymentHandler> = [CardHandler, PaypalHandler];
export const PAYMENT_HANDLER_LIST = new InjectionToken<PaymentHandler[]>('PAYMENT_HANDLER_LIST');

export function provideImplscan(): Provider[] {
  return [
    { provide: PAYMENT_HANDLER_LIST, useClass: CardHandler, multi: true },
    { provide: PAYMENT_HANDLER_LIST, useClass: PaypalHandler, multi: true },
  ];
}
```

There is one token per marked interface, and `provideImplscan()` registers all of them.
</details>

The [example](example/main-angular.ts) in this repository resolves the generated providers
through Angular's real injector (`npm run start:angular`).

#### Without Angular

The default target generates plain arrays of classes, with no framework dependency. It works for
Node, other frameworks, or plain TypeScript:

```json
"scripts": {
  "generate": "ts-implscan",
  "prestart": "npm run generate",
  "prebuild": "npm run generate"
}
```

```ts
import { PaymentHandlerImplementations } from './generated/implscan-registry';

const handlers = PaymentHandlerImplementations.map((Handler) => new Handler()); // PaymentHandler[]

for (const handler of handlers) {
  console.log(handler.pay(42));
}
```

If your implementations have dependencies, register the classes from the array with your DI
container instead of calling `new`.

<details>
<summary>What gets generated</summary>

```ts
// src/generated/implscan-registry.ts
// GENERATED by ts-implscan – do not edit
import type { PaymentHandler } from '../payment/payment-handler';
import { CardHandler } from '../payment/card-handler';
import { PaypalHandler } from '../payment/paypal-handler';

export const PaymentHandlerImplementations: Array<new (...args: any[]) => PaymentHandler> = [CardHandler, PaypalHandler];
```
</details>

The [example](example/main.ts) in this repository does exactly this (`npm start`).

**That's it.** A new implementation is picked up the next time the generator runs. A new
interface only needs `extends ImplScan`, and with Angular its token is generated too.

## Dispatching to one implementation

Often you don't want *all* implementations but *the right one*: the payment handler for the
selected method, the exporter for the chosen format. Extend `Dispatchable<TContext>` instead of
`ImplScan`, and let every implementation say when it applies:

```ts
// payment-context.ts
export interface PaymentContext {
  method: 'card' | 'paypal' | 'twint';
}

// payment-handler.ts
import type { Dispatchable } from '@thomasrepnik/ts-implscan';

export interface PaymentHandler extends Dispatchable<PaymentContext> {
  name: string;
  pay(amount: number): string;
}

// card-handler.ts
export class CardHandler implements PaymentHandler {
  name = 'card';
  isApplicableTo(context: PaymentContext) {
    return context.method === 'card';
  }
  getPriority() {
    return 10; // higher wins when several handlers apply
  }
  pay(amount: number) {
    return `charged ${amount} to credit card`;
  }
}
```

The generator still writes the list and its token, and additionally a `PaymentHandlerDispatcher`
class that implements `PaymentHandler` and forwards every member to the applicable implementation.
The only thing it can't know is where the context comes from, so you provide that.

#### With Angular

`provideImplscan()` registers the dispatcher. Provide the generated context token with a
**function** that returns the current context. It is called on every dispatcher call, so a
`Signal` works as well as a plain function:

```ts
// app.config.ts
providers: [
  provideImplscan(),
  // static: read the method once at startup
  { provide: PAYMENT_HANDLER_CONTEXT, useFactory: () => { const method = inject(PAYMENT_METHOD); return () => ({ method }); } },
  // reactive: a Signal<PaymentContext> is already a () => PaymentContext
  // { provide: PAYMENT_HANDLER_CONTEXT, useFactory: () => inject(PaymentSettings).context },
]

// anywhere
private readonly payment = inject(PaymentHandlerDispatcher);
this.payment.pay(42); // forwarded to CardHandler, PaypalHandler or TwintHandler
```

A component or route can use its own context: provide `PAYMENT_HANDLER_CONTEXT` **and**
`PaymentHandlerDispatcher` in that injector's `providers`. The class has no constructor arguments
and no decorator, so the bare class name works as a provider.

#### Without Angular

The plain dispatcher takes the implementations and the context function in its constructor:

```ts
let method: PaymentContext['method'] = 'twint';
const payment = new PaymentHandlerDispatcher(handlers, () => ({ method }));
payment.pay(42); // TwintHandler
method = 'card';
payment.pay(42); // CardHandler: applicable with priority 10, PaypalHandler only has 0
```

#### How the delegate is chosen

On **every call**, the dispatcher reads the context and filters the implementations with
`isApplicableTo(context)`:

- none applicable: throws, naming the context and all candidates with their priorities
- exactly one: used, whatever its priority
- several: the highest `getPriority()` wins
- a tie for the highest priority: throws, naming the tied candidates

Because the choice is made per call, a context that changes between calls switches the
implementation, and nothing is resolved while the injector is still being built. Two things
follow: keep `isApplicableTo` cheap and free of side effects, and remember that with a changing
context a stateful setter and a later call may land on different implementations.

<details>
<summary>What gets generated</summary>

```ts
export const PAYMENT_HANDLER_CONTEXT = new InjectionToken<() => PaymentContext>('PAYMENT_HANDLER_CONTEXT');

export class PaymentHandlerDispatcher implements PaymentHandler {
  private readonly implementations = inject(PAYMENT_HANDLER_LIST);
  private readonly context = inject(PAYMENT_HANDLER_CONTEXT);

  private get delegate(): PaymentHandler {
    return resolveDelegate('PaymentHandlerDispatcher', this.implementations, this.context());
  }

  isApplicableTo(context: PaymentContext): boolean {
    return this.delegate.isApplicableTo(context);
  }

  getPriority(): number {
    return this.delegate.getPriority();
  }

  get name(): string {
    return this.delegate.name;
  }

  set name(value: string) {
    this.delegate.name = value;
  }

  pay(amount: number): string {
    return this.delegate.pay(amount);
  }
}

// inside provideImplscan()
{ provide: PaymentHandlerDispatcher, useClass: PaymentHandlerDispatcher },
```

Signatures are copied from the interface, and the types they use are imported into the
generated file. `resolveDelegate` is emitted once per generated file. The plain target has the
same class with a constructor instead of `inject()`.
</details>

## Good to know

- **Check what would be collected** without writing anything: `npx ts-implscan --dry-run`.
- **Replace a whole list in Angular tests** with one provider:
  `providers: [{ provide: PAYMENT_HANDLER_LIST, useValue: [fakeHandler] }]`.
- **A marked interface without implementations** gives an empty array, and in Angular a
  `useValue: []` provider, so injecting it doesn't throw. A dispatcher over an empty list throws
  on its first call.
- **The Angular dispatcher comes from DI**, through `provideImplscan()` or by re-providing the
  class. Creating it with `new` fails, because its fields use `inject()`.
- **Commit the generated file**, so the IDE and type checks work right after a checkout. Let CI
  catch a forgotten regeneration with `npm run generate && git diff --exit-code`.
- **In CI**, `prebuild` only runs through `npm run build`. If your pipeline calls `ng build`
  directly, run `npm run generate` first.

## Why

In Spring you can inject `List<PaymentHandler>`, and the container hands you every bean that
implements the interface. TypeScript can't do this out of the box, for two reasons:

1. **Interfaces are erased.** At runtime nothing records that a class implements `PaymentHandler`.
2. **There is no classpath scanning.** JavaScript only runs files that something imports, so a
   new implementation that nobody imports doesn't exist at runtime.

DI containers such as Angular, tsyringe or InversifyJS solve this with injection tokens, but
then you have to register every implementation by hand, and it's easy to forget one.

`ts-implscan` moves the scan to build time. It uses [ts-morph](https://ts-morph.com) and the
TypeScript type checker to find every exported class that `implements` a marked interface. The
generated file is ordinary TypeScript, so `tsc` fails if a listed class doesn't actually satisfy
its interface.

**Why a marker interface rather than a comment tag like `/** @implscan */`?** The marker is
checked by the compiler, so a typo doesn't silently drop the interface. Your IDE's "Find usages"
on `ImplScan` lists every collected interface, and renames are safe. It's the same idea as a Java
marker interface such as `Serializable`, and it keeps out the interfaces you implement for other
reasons, such as Angular's `OnInit`.

## When it's helpful

- **Plugin and strategy patterns**, such as payment providers, exporters, validators, notification
  channels or feature handlers, where the set of implementations keeps growing.
- **Teams coming from Spring or Java** who want the open/closed principle that `List<PaymentHandler>` injection
  gives them: adding behaviour means adding a class, not editing a central list.
- **Angular apps** with many multi-provider tokens, so nobody forgets to register a new
  implementation, or to write the token.

It's probably overkill if you have two implementations that rarely change. A hand-written array
is fine then.

## CLI options

```sh
ts-implscan [--project tsconfig.json] [--src src] [--out src/generated/implscan-registry.ts] [--target plain|angular] [--dry-run]
```

| Option       | Default                              | Meaning                                                  |
|--------------|--------------------------------------|----------------------------------------------------------|
| `--project`  | `tsconfig.json`                      | tsconfig to read compiler options from (paths, resolution) |
| `--src`      | `src`                                | Folder to scan. `*.spec.ts` and `*.d.ts` are skipped.      |
| `--out`      | `src/generated/implscan-registry.ts` | File to generate                                         |
| `--target`   | `plain`                              | `angular` adds an `InjectionToken` per interface and `provideImplscan()` |
| `--dry-run`  | off                                  | Print the result to stdout instead of writing it         |
| `-h, --help` |                                      | Show the help                                            |

The files to scan come from `--src`, not from the tsconfig, because a new implementation isn't
imported anywhere yet. The tsconfig is only read for compiler options. The import extension in
the generated file follows it too: `.ts` with `allowImportingTsExtensions`, `.js` with `NodeNext`,
and no extension with `bundler`, which is what Angular uses.

## Limits

- Only interfaces that extend `ImplScan` or `Dispatchable` **directly** are collected. The CLI
  detects the markers by name, so a local `interface ImplScan {}` works too; a local `Dispatchable`
  must declare the same two members.
- Only explicit `implements X` clauses count. Classes that only match the interface structurally,
  and subclasses of an implementing class, are not found.
- Implementations must be exported, non-abstract, named-export classes. A non-exported
  implementation is skipped with a warning.
- A dispatcher forwards property writes through a setter; `readonly` properties get no setter.
- Some interface shapes get a warning and no dispatcher (the list and token are still generated):
  overloaded or optional members, destructured parameters, accessors, `this` return types, index
  or call signatures, generic interfaces, members inherited from a generic base other than
  `Dispatchable`, signatures using non-exported types, and two imported types sharing one name.
- `isApplicableTo` runs on every dispatcher call; keep it cheap.

## Development

This repository contains the library in `src/` and a runnable demo in `example/`. The demo has
two marked interfaces: `PaymentHandler` (`Dispatchable`, with a generated dispatcher) and
`Notifier` (`ImplScan`, a plain list).

```sh
npm install
npm run generate:dry           # print the plain registry for the example, write nothing
npm run generate:dry:angular   # the same with Angular tokens and providers
npm start                      # regenerate, then run the example with plain arrays
npm run start:angular          # regenerate, then resolve everything through Angular's real Injector
npm run typecheck
npm test                       # generator tests (in-memory ts-morph projects) and the generated dispatcher
npm run test:package           # pack, install into an empty project, run the CLI from there
```

`@angular/core` and `rxjs` are dev dependencies only so that `start:angular` can run Angular's
injector in Node. The published package only depends on `ts-morph`.

### Releasing

Releases are uploaded to npm by `.github/workflows/release.yml`, using npm
[trusted publishing](https://docs.npmjs.com/trusted-publishers). It doesn't need an npm token.

```sh
npm version minor            # or patch / major: bumps package.json, commits and tags vX.Y.Z
git push --follow-tags
gh release create v0.2.0 --generate-notes   # or click "Publish release" on GitHub
```

Publishing the GitHub release starts the workflow. It checks that the tag matches
`package.json`, type-checks, runs the package smoke test and **stages** the version on npm.
A staged version isn't public until a maintainer approves it with 2FA:

```sh
npm stage list @thomasrepnik/ts-implscan   # shows the stage id
npm stage approve <stage-id>
```
